Digital Dairy Management System

This is a simple architecture for a local dairy shop. It replaces the notebook: daily milk entries, automatic monthly bills, and a clear list of who has paid and who still owes money.

The problem

Small dairy owners write daily milk purchases in a notebook and add up monthly bills by hand, which leads to mistakes and wasted time. They also struggle to remember who has paid. This system keeps a digital record of all of it. The owner gets full access, and customers can optionally view their own records.

1. System architecture

Example: the owner enters “Ramesh, 2 L, ₹60/L”. The frontend sends it to the backend, which checks it and calculates ₹120, then saves it into milk_record. The backend replies “Saved”, and the page updates.

2. Database (ER) diagram

Relationships: this is a single-shop system, so the owner table only stores the shop owner's login and isn't linked to other tables. One customer has many milk records and many bills (one per month). One bill can have many payments, which allows partial payments.

Why is the rate stored on every milk record? If the milk price changes next month, old bills stay correct. Pending amount = total_amount − amount_paid.

3. The architecture in simple words

Think of it like a restaurant. There are three layers, and each has one job:

Frontend = menu & tableThis is what you see and click: forms, buttons and tables. It only shows things and sends your requests.
Backend = waiter & kitchenIt takes each request, checks that you are logged in, checks the input (no negative litres!), and does all the maths.
Database = storeroomIt keeps all the data safely and permanently in five organised tables.

A normal day

  1. The owner logs in. The password is checked against a secure hash, and a session keeps them logged in.
  2. They open Daily Entry, pick a customer and type the litres. The rate fills in from the customer's default rate.
  3. The backend calculates amount = quantity × rate and saves one row in milk_record.

End of the month

  1. The owner clicks Generate Bills.
  2. For each customer, the backend adds up that month's records (SUM(quantity), SUM(amount)) and saves one row in bill.
  3. When a customer pays, a row is added to payment. The bill's amount_paid goes up, and its status changes to Partial or Paid.

Dashboard: just three simple queries

  • Total customers: COUNT of active customers
  • This month's sales: SUM(amount) of this month's milk records
  • Pending payments: SUM(total_amount − amount_paid) over bills that are not fully paid

Customer view (optional, build it last)

The customer logs in with their phone number and a PIN. They can only see their own milk history and bills, and they can't change anything.

4. Beginner-friendly tech stack

LayerChoiceWhy
FrontendHTML, CSS, Bootstrap, plain JavaScript (or EJS templates)Nothing new to learn first, and pages look good on a phone
BackendNode.js + ExpressJavaScript everywhere, with many tutorials
DatabaseMySQL (or SQLite for the easiest setup)The data fits naturally into linked tables
Loginexpress-session + bcryptSimple, and passwords are never stored as plain text
ToolsVS Code, Postman, MySQL Workbench, Git/GitHubAll free and widely used
HostingRender or Railway (free tier)Easy to deploy

If you prefer Python: Flask + SQLite + Bootstrap works just as well.
Left out on purpose: React, microservices, Redis, and a mobile app. A single shop doesn't need them.
